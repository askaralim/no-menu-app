# 酒款上新与图片识别流程

本文记录小程序与 POS 已实现的统一约定。两端可使用不同组件，但入口、状态、字段优先级与保存语义必须一致。POS production OTA 与 hotfix 记录见 [`POS_RECOGNITION_OTA_2026-10-23.md`](./POS_RECOGNITION_OTA_2026-10-23.md)。

## 范围与主流程

- 识图只允许从相册/文件选择电子图片，不提供拍照。
- 首版填写酒款中英文名、风格、ABV、酒厂和联名酒厂；不填写酒桶或包装容量。
- AI 服务只返回草稿，不写 Supabase。
- 相册原图最大 5MB；正式保存前压缩到最长边 1200px、JPEG 约 75%，持久化文件仍不得超过 2MB。

```text
上新 -> 添加到 #n
  ├─ 上传图片识别（主入口）-> 相册 -> 识别
  │    ├─ 本店唯一匹配：直接上酒 / 编辑后上酒
  │    ├─ 商品池唯一匹配：带入资料与商品池图片后编辑
  │    └─ 无唯一匹配：带入识别草稿和所选图片后新增
  └─ 搜索或手动新增（次入口）-> 编辑页
       ├─ 输入酒名 -> 本店未上酒单商品 / 全局商品池
       ├─ 未命中 -> 可原地上传图片识别
       └─ 不搜索 -> 直接手动填写
```

## 统一入口

1. 首屏只展示两个同级选择：主入口“上传图片识别”和次入口“搜索或手动新增”。
2. 识图同时尝试匹配本店和全局商品池，因此不再单独提供首屏“搜索已有酒款”入口。
3. 手动编辑页的酒名输入仍是搜索框；输入后立即过滤本店未上酒单商品，停止输入 250ms 后调用 `search_drink_products`。两组结果独立展示，只隐藏与本店结果具有相同 `product_id` 的全局重复项。
4. 搜索未命中时就地提供“上传图片识别”，不要求用户返回入口页。
5. 从编辑页转识图时保留已填草稿；识别或商品池匹配只补全空白字段，不覆盖用户已填内容。

## 识别页状态

- 识别中：图片预览、文字状态、取消识别。取消后忽略未完成响应并返回，不产生写入。
- 失败：可读错误、重新上传、返回。重新上传仍只打开相册；如果用户取消相册，保留原错误状态。
- 完成：显示来源、酒名、英文名、酒厂、风格、ABV、联名酒厂；不自动跳转，等待用户确认。
- 换图：先保留当前结果；只有用户实际选中下一张图片后才清空旧结果并发起新请求。取消系统相册不会进入空 loading。

## 名称与匹配

稳定客户端字段：

```json
{
  "name": "漫长的季节",
  "nameCn": "漫长的季节",
  "nameEn": "One Year Later"
}
```

- `name = nameCn || nameEn`，保持旧客户端兼容。
- Prompt 只提取图片明确出现的名称，繁体转简体；只有英文时不得生成中文译名。
- 精确匹配同时使用三个名称字段，对比本店/商品池中英文名称。
- 仅有一个精确结果才自动标记匹配；重复或模糊结果按未匹配处理。

## 图片与数据优先级

- 本店直接上酒：使用本店现有资料与图片。
- 商品池匹配：使用商品池资料与图片。
- 未匹配：使用识别草稿与用户所选图片，中文名优先、英文名兜底。
- 临时图片仅发送给 AI；只有编辑页确认保存后才通过 `uploadDrinkImage` 正式上传。
- 5MB 是原图选择和识图请求上限，不是最终存储上限；最终上传前压缩并继续执行 2MB 校验。
- 编辑页图片区域只负责上传或更换图片；只有搜索未命中提示提供识图快捷入口。
- 取消、返回或识别失败都不创建商品、不上传正式图片。

## 目标酒头与保存语义

- 从空酒头 `#n` 发起新增时，`#n` 是本次流程的固定上下文。关闭入口弹框、等待 iOS `onDismiss`、识图、换图、编辑和保存都不得重新从页面当前状态推导酒头。
- POS 在 `CatalogPickSheet` 关闭前冻结 `targetTapNumber`，打开 `DrinkEditSheet` 时作为 `suggestedTapNumber` 传入，保存时再显式传给 `saveDrinkWithIntent`。
- “保存并上到 #n”包含两个已有操作：先保存或更新商品，再调用 `set_drink_taplist_listing` 关联目标酒头。不要把商品保存成功等同于上酒成功。
- 两步都成功后，父页面先乐观合并已保存酒款，再刷新酒单草稿，用户返回酒单时应立即看到新酒款。
- 如果商品已保存但酒头关联失败，保留编辑器、已保存商品 ID 和目标酒头，提示“商品已保存，尚未上枪”。重试不得再创建一条重复商品。

## 鉴权与调用约束

- 识别请求携带当前 Supabase access token。
- AI 服务验证用户和门店成员资格，并使用短时缓存减少重复 Supabase 调用。
- 空搜索不调用 RPC；识图有名称且未匹配本店时只查询一次商品池。
- 客户端取消会通过 `AbortController` 停止等待并使迟到结果失效；请求若已进入服务端或模型提供方，不保证同时终止服务端计算。

## POS 组件与 Modal 生命周期

- `components/taplist/CatalogPickSheet.tsx`：两个新增入口和相册选择。
- `components/taplist/DrinkEditSheet.tsx`：识别状态、搜索结果、编辑与保存。
- `lib/beerLabelRecognition.ts`：鉴权、请求、超时与返回归一化。
- `lib/taplistMedia.ts`：5MB 原图校验、设备端压缩和 2MB 最终上传校验。

iOS 不允许在前一个原生 Modal 尚未完成 dismiss 时可靠 present 下一个 Modal。新增方式弹框必须先关闭，并在 `onDismiss` 后再打开识图编辑器。Web / Android 在关闭渲染后的下一任务继续。不要把这两个状态重新合并到同一帧更新。

## 小程序代码位置

- `pages/product-picker/`：统一入口
- `pages/drink-recognition/`：识别状态和结果确认
- `pages/drink-editor/`：最终编辑、上传和保存
- `services/ai.js`：图片压缩、鉴权和 AI 请求
- `utils/drink-recognition.js`：中英文名称精确匹配
