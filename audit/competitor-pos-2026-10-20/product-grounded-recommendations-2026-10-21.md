# No Menu 订单体验：基于现状的竞品学习与产品建议

日期：2026-10-21  
范围：No Menu Tonight `mobile/`、生产 Supabase 聚合数据、竞品 iPhone 实机流程  
原则：不假设接入支付，不把 No Menu 重构为完整餐饮 POS

## 1. 结论

No Menu 应继续优化订单，但当前最合理的产品定义是：

> **与实时酒单共用商品和价格的轻量消费记录工具。帮助酒吧快速开单、加单、结单和回看；资金仍由线下或其他系统处理。**

不建议现在复制竞品完整的桌台、收银、退款、会员和库存体系。订单模块目前有真实、持续的单店使用，但覆盖面很小，尚不足以支持全产品转向完整 POS。

最应学习的是竞品的交互方法，而不是功能总量：

1. 每个页面只处理一个清晰任务。
2. 操作后立即给出数量、状态和金额反馈。
3. 当前动作固定在拇指区，次要动作进入统一底部面板。
4. “进行中、已完成、已作废”等状态有清晰、可信且可恢复的边界。
5. 用户退出再回来，工作仍能从原处继续。

## 2. 当前产品定位

当前公开定位是“酒吧实时酒单管理与发布工具”，核心闭环是：

`商品库 → 今晚酒单/固定酒头 → 网页/二维码/顾客 App/小程序同步`

订单属于平台控制的可选能力：

- 默认 `ordering_enabled = false`。
- 开启后增加“开台”和“订单”入口。
- 店主指南明确说明“不处理收款，只记录谁喝了什么、多少钱”。
- App Store 对外描述也明确“不处理支付、交易或配送”。

因此，订单优化的战略价值主要是：

- 提高已合作酒吧的日常使用频率和留存。
- 让商品价格与实际消费记录形成闭环。
- 为未来判断库存、热销、会员等能力是否值得做提供数据。

它目前不是获客主卖点，也不应影响未开启订单的绝大多数门店。

## 3. 生产数据现状

以下为 2026-10-21 的生产库只读聚合结果。金额是系统记录的订单总额，不代表真实到账。

| 指标 | 当前值 | 判断 |
| --- | ---: | --- |
| 门店租户 | 69 | 已有一定商户基础 |
| 开启订单功能 | 5（约 7.2%） | 覆盖率低，应继续 feature gate |
| 历史有订单的门店 | 2 | 采用非常集中 |
| 最近 30/90 天有订单的门店 | 1 | 当前价值主要来自单店 |
| 最近 30 天订单 | 106 | 单店持续使用，不是一次性点击 |
| 最近 30 天有订单日期 | 19 天 | 接近规律性运营使用 |
| 最近 30 天记录金额 | ¥20,024 | 只可称记录金额/结单金额，不能称实收 |
| 最近 30 天平均订单金额 | ¥188.91 | 符合酒吧消费记录量级 |
| 最近 30 天平均订单结构 | 1.99 条明细、3.40 件 | 订单较简单，暂不支持复杂拆单需求 |
| 最近 90 天平均单日订单 | 4.47 单；最高 15 单 | 不是高并发餐饮桌台场景 |
| 当前进行中旧单 | 15，全部超过 7 天 | 状态清理/作废比桌台转移更急 |

### 数据不能证明的事情

- 无法只凭数据库确定这家活跃门店是在正式营业使用，还是长期内部测试。
- 无法确定它是否把 No Menu 当唯一 POS，还是与另一套支付/POS 并行使用。
- 无法知道未启用门店是不需要订单，还是没有被培训/开通。
- 没有操作事件数据，无法测量开一单耗时、误触、放弃和恢复原因。

这些问题必须通过门店访谈和小范围试点验证，不能从竞品功能数量推断。

## 4. 当前数据结构能做什么

### 已有基础

- `orders`：顾客名称、状态、订单日期、总额、营业日、备注、结单时间。
- `order_items`：酒款、规格、数量、价格快照、规格名称快照。
- `business_days`：开店/结束营业日与不可逆关闭保护。
- `ordering_enabled`：按门店控制是否出现订单能力。
- 酒款规格已经有 `volume_ml`，未来可以支持容量相关分析。
- 酒单、商品、价格和订单使用同一套酒款/规格数据。

### 当前缺失

- 桌台、区域、人数、桌台容量。
- 草稿/待下单/已下单批次。
- 作废/取消状态及原因。
- 收款方式、实收、找零、优惠、退款等资金流水。
- 酒桶批次、初始容量、剩余量、成本与人工盘点。
- 拆单、并单、转桌的数据模型。

### 必须先处理的数据安全问题

当前订单编辑会先更新名称，再删除全部 `order_items`，最后重新插入。创建订单也会先插入订单，再插入明细。任一步中途失败，都可能产生空单或部分更新。

这比 UI 改版更优先：应先用一个事务型 RPC 原子完成订单及明细的创建/更新。

## 5. 建议立即做：成熟化轻量订单，而不是扩张功能

### P0-A：订单写入原子化

**必要性：高；成本：S–M（约 2–4 个工程日 + 回归）。**

- 新增一个 tenant-scoped RPC，一次完成订单和明细写入。
- 创建失败不留下空订单；编辑失败保留原明细。
- 保留当前价格/规格快照行为。
- 补并发编辑和营业日已关闭测试。

这是继续优化任何订单 UI 之前的前置条件。

### P0-B：增加“作废订单”，修复状态可信度

**必要性：高；成本：M（约 3–5 个工程日）。**

- 增加 `voided`/`cancelled` 状态、原因与时间；不物理删除。
- 进行中超过一个营业日时显示“未完成旧单”提示。
- 结束营业日前提供明确的未完成单处理入口。
- 经营数据排除作废单，单独显示数量。

生产库已有 15 张超过 7 天的进行中单，这是当前最直接的证据。

### P0-C：优化现有开单界面，但不引入桌台 schema

**必要性：高；成本：M（约 5–8 个工程日）。**

- 将“客户姓名”改为 **订单名称**，提示“顾客称呼、桌号或自定义名称”。保持现有用户习惯，也允许门店自行使用桌号。
- 商品页采用稳定的分类导航 + 商品网格；单规格点击即加入，多规格才弹选择。
- 加入商品时同时更新商品卡数量和底部购物车数量。
- 底部固定显示件数、金额和唯一主操作。
- 购物车使用底部面板编辑数量，不再让已选商品把商品目录整体推到下方。
- 创建/更新成功后显示明确反馈，并回到对应进行中订单。
- 本地暂存未提交购物车，意外退出后可继续。

这部分直接学习竞品的“流畅”，但不改变业务边界。

### P0-D：纠正金额语义

**必要性：高；成本：S（1–2 个工程日）。**

- 没有支付事实时，不把总额展示为“实收”或已验证“营业额”。
- 建议用“订单记录金额”“已结单金额”或“应收记录”。
- 结单确认中明确：“No Menu 不处理支付，请确认已在线下或其他系统完成处理。”
- 是否把“结账”改为“结单”应先询问当前活跃门店，避免破坏熟悉术语。

## 6. 建议先验证，再决定开发

### V1：可选桌台模式

**证据强度：弱；成本：L（约 2–4 周）。**

当前数据没有显示桌号命名习惯，且平均单日订单不高。不要直接把所有门店切成桌台网格。

验证方式：

1. 访谈当前活跃订单门店：如何命名订单、有没有固定桌号、是否频繁找错单。
2. 询问 4 家已开启但未使用的门店：不用订单的首要原因。
3. 做一个只在试点门店出现的“列表 / 桌台”模式原型。
4. 至少两家独立门店明确要求并愿意连续试用，再建 table/area/guest schema。

### V2：待下单 / 已下单

**证据强度：中；成本：L（约 2–4 周）。**

如果 No Menu 只由同一个吧台人员记账，当前“保存订单”已够用。只有当订单需要交给另一个人制作/出品时，才需要批次、制作状态和撤回规则。

先问：

- 谁点单、谁出酒？
- 保存后是否代表已经通知制作？
- 加点时是否发生过漏做或重复做？

没有跨角色交接，就只优化保存反馈，不引入复杂状态机。

### V3：外部收款记录

**证据强度：未知；简单版本成本 M，完整版本成本 XL。**

可以考虑的最小版本不是支付，而是可选记录：

- “已在线下处理”
- 可选方式：现金 / 微信 / 支付宝 / 其他系统 / 未记录
- 可选备注

它不能声称支付成功，也不能成为真实对账依据，除非门店明确只用 No Menu 记账并愿意维护这些字段。

解锁条件：至少两家门店明确表示需要按外部收款方式复盘，且愿意持续录入。

### V4：酒桶库存与余量

**证据强度：竞品强、我方用户证据弱；成本：XL（约 4–8 周）。**

竞品这部分确实优秀，但它需要：桶批次、初始容量、损耗、试饮、赠饮、手工校准、换桶和成本录入。只按订单容量扣减会制造“看似精确、实际错误”的库存。

应先验证门店是否愿意录入每桶初始容量和换桶动作。若不愿意，优先保留现有售罄/上新流程，不做伪精确余量。

## 7. 当前阶段不要做

- 微信/支付宝支付接入或“支付成功”状态。
- 现金收款键盘、找零计算器、多支付方式组合。
- 储值、会员余额、优惠券和复杂折扣审批。
- 拆单、并单、转桌的完整模型。
- 厨房打印、出品队列、外卖渠道。
- 自动酒桶库存和毛利报表。
- 把订单能力默认开放给全部门店。

这些能力会把产品带入完整 POS 的实施、培训、财务准确性和售后责任，而当前采用数据不足以支撑。

## 8. 建议的产品试点

### 第 1 阶段：可靠性与流畅度（2–3 周）

- 原子订单 RPC。
- 作废/旧单处理。
- 订单名称兼容顾客和桌号。
- 商品选择、购物车反馈、固定主按钮和草稿恢复。
- 金额语义修正。

仅对当前 `ordering_enabled` 门店开放，不改变默认产品。

### 第 2 阶段：验证 4 周

至少记录：

- 每周活跃订单门店数。
- 每家每周订单数和有订单天数。
- 开单后成功创建比例。
- 创建/更新失败和空单数量。
- 超过 24 小时仍进行中的订单比例。
- 作废率、恢复率、继续加点率。
- 门店主观反馈：是否比之前更快、是否仍依赖另一套 POS、最缺哪一个动作。

建议解锁下一阶段的门槛：

- 至少 3 家独立门店连续 4 周每周使用订单；或
- 至少 2 家独立门店提出同一个具体流程需求，并愿意试用。

### 第 3 阶段：按证据选择一个方向

- 如果痛点是找台：做可选桌台模式。
- 如果痛点是漏做：做待下单/已下单与出品状态。
- 如果痛点是对账：做外部收款记录。
- 如果痛点是桶损耗：做桶批次试点。

不要四条路线同时启动。

## 9. 从竞品借鉴的交互规则

1. 页面顶部始终回答“我在哪、当前对象是谁”。
2. 商品点击后，商品卡、分类和底部汇总同时反馈。
3. 主操作固定在底部，文字包含结果，例如“创建订单 · 3 件 · ¥168”。
4. 次要操作使用统一底部面板，不堆在页面正文。
5. 危险动作独立成红色区域，说明后果并允许合理恢复。
6. 空状态不仅说“没有”，还告诉用户下一步。
7. 状态文案使用业务事实，不假装掌握系统不知道的支付结果。
8. 视觉上保留 No Menu 深色金色品牌，不复制竞品黑白绿皮肤。

## 10. 最终优先级

| 优先级 | 项目 | 现在是否做 |
| --- | --- | --- |
| P0 | 原子创建/更新订单 | 做 |
| P0 | 作废、旧单提醒与清理 | 做 |
| P0 | 现有点单页交互和反馈优化 | 做 |
| P0 | 金额/结单语义校准 | 做 |
| P1 | 订单使用指标与门店访谈 | 做 |
| P2 | 可选桌台模式 | 达到验证门槛后做 |
| P2 | 待下单/已下单 | 有跨角色出品需求后做 |
| P2 | 外部收款方式记录 | 有明确对账需求后做 |
| P3 | 酒桶库存生命周期 | 有稳定录入意愿后试点 |
| 暂缓 | 支付接入、会员储值、复杂拆单/退款 | 不做 |

## 11. 证据与限制

- 竞品实机已覆盖桌台、开台、点单、订单详情、整单动作、收款、折扣、酒头、经营和设置。
- 本轮继续补测挂单/转桌/拆单时，iPhone 镜像要求输入 Mac 登录密码，因此没有继续进入这些子流程。
- 生产数据只做了聚合只读查询，没有修改任何记录。
- 工期为一名熟悉当前 React Native + Supabase 代码的工程师的粗估，不含 App Store 审核等待和门店现场培训。
